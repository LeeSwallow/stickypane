# ADR-0019. 앱 하나만 깔면 된다: 터미널 명령은 암호 없이 링크하고, 에이전트는 앱의 stickypane으로 잇는다

| 항목 | 값 |
|---|---|
| 상태 | Accepted |
| 날짜 | 2026-10-29 |
| 관련 요구 | R-44, #22 |

## 맥락

사용자 결정(R-44): 앱만 깔면 다 된다. 앱은 `stickypane`을 안에 가지고 있다(Contents/Helpers). 터미널과 에이전트는 PATH의 `stickypane`을 부르는데, 그 PATH에는 예전에 Homebrew로 깐 0.1.1 같은 옛 사본이 먼저 있을 수 있다. GUI 앱의 PATH는 사용자의 셸과 다르고, 앱이 setup을 띄우면 작업 폴더가 `/`나 `$HOME`이 되기 쉽다(#26에서 옛 setup이 그 자리에 보드를 만들었다). 앱은 TS로 테마 팔레트 사본을 두었다(RA9).

## 결정

- 터미널 명령은 **링크**다. 기본은 `~/.local/bin/stickypane`, 암호 없이. `/usr/local/bin`은 사용자가 고를 때만 시스템 암호 창으로. 앱이 둔 것이 아닌 파일은 묻고 나서 바꾸고, 제거는 앱의 링크만 지운다.
- 터미널이 무엇을 먼저 쓰는지는 로그인 셸의 PATH로 판단하고, 앞선 옛 사본은 경로·버전·고치는 법(brew uninstall, 또는 PATH 순서)으로 알린다. 앱이 옛 사본을 지우지는 않는다.
- 에이전트 연결은 앱의 `stickypane setup --scope user`를 앱이 만든 빈 임시 폴더에서 돌리고, 계획(`--dry-run`)을 먼저 보인다. MCP 서버는 `--command`로 전체 경로를 등록한다(앱의 링크, 없으면 앱 안의 사본).
- `stickypane init`은 홈 폴더와 루트를 거절한다(본체에서도). 앱의 `refuseInit`은 그대로 둔다.
- 테마 목록과 짝 팔레트는 bridge의 `themes.list`에서 받는다. 앱 런타임에는 팔레트 사본이 없고, dev 페이지와 테스트용 픽스처(`demo/themes.json`)만 `scripts/palettes`의 Go 테스트가 최신으로 지킨다. bridge가 없는 홈 창의 두 기본 팔레트(`fallback.ts`)는 그 픽스처와 같은지 테스트한다.

## 결과

- sudo 없이 설치된다. 대신 `~/.local/bin`이 PATH에 없는 사람은 한 줄을 직접 넣어야 한다. 앱은 그 줄과 파일을 보인다.
- MCP 등록이 앱의 경로를 가리키므로 앱을 옮기면 링크를 다시 걸어야 한다. 링크를 쓰면 앱 업데이트는 그대로 따라간다.
- 플러그인의 훅과 MCP 설정은 여전히 PATH의 `stickypane`을 부른다. 앞선 옛 사본 경고가 그 틈을 메운다.
- 옛 bridge(`themes.list`가 없는)를 쓰면 테마 목록에 고른 것만 보이고, 모드가 짝을 원해도 고른 테마의 색이 남는다.
