# stickypane 설계

- 작성일: 2026-10-01
- 상태: 검토 대기
- 이름: `stickypane`. 정한 이유와 제외한 후보는 14절에 있다.

## 1. 목적

AI 코딩 에이전트(Claude Code, Codex 등)가 편하게 끄적이고, 사람이 터미널에서 바로 훑어보고 고치는 **노트 보드**를 만든다. tmux나 wezterm에서 창을 나눠 옆에 띄워 두면, 에이전트가 진행 상황·보고서·로그를 노트로 붙이고 갱신하고, 사용자가 같은 화면에서 확인하고 수정한다.

오픈소스로 배포하는 작은 사이드 프로젝트다.

### 정체성

격식 있는 프로젝트 관리 도구가 아니라 벽에 붙이는 메모지에 가깝다. 낙서하듯 가볍게 쓰고, 지나가다 보고, 다 쓰면 떼어 낸다. 이 느낌이 다음 원칙으로 이어진다.

1. **가장 쉬운 길이 기본값이다.** 마크다운 한 줄만 있는 파일도 온전한 노트다. 머리말도, 제목도, 종류 지정도 필요 없다.
2. **종류보다 노트가 먼저다.** 화면에 붙는 것은 모두 노트다. 칸반·체크리스트·로그는 노트가 가질 수 있는 모양일 뿐이다.
3. **틀려도 괜찮다.** 형식이 어긋나도 내용을 숨기거나 잃지 않는다.
4. **보기에 친근하다.** 노트마다 색이 있고 모서리가 둥글다. 표나 대시보드처럼 보이지 않는다.

### 배경: 이전 시도가 실패한 이유

wezterm Lua 설정과 워크플로우 훅으로 만든 이전 상태 표시는 들인 노력에 비해 얻는 것이 적었다. 원인은 셋이다.

1. 설정·유지비가 컸다. Lua, 훅, 상태 정의를 계속 손봐야 했다.
2. 특정 워크플로우와 특정 터미널에 묶여 다른 프로젝트에서 쓸 수 없었다.
3. 에이전트 부담이 컸다. 상태를 갱신하려고 에이전트가 매번 전용 명령을 실행해야 했고, 빼먹으면 화면이 틀어졌다.

이 셋을 반복하지 않는 것이 설계의 제약이다.

### 성공 기준

- 설치 후 `stickypane init`, `stickypane` 두 명령으로 설정 파일 없이 화면이 뜬다.
- 에이전트는 `init`이 넣어 준 안내문만 읽고, 평소 쓰는 파일 편집만으로 네 가지 모양의 노트를 만들고 갱신한다. Claude Code와 Codex에서 직접 확인한다.
- 폭 40칸짜리 좁은 분할 pane에서도 읽을 수 있다.
- 새 모양을 추가할 때 새 패키지 하나와 등록 한 줄만 건드린다.

## 2. 기존 도구 조사

2026-10-01 기준으로 같은 구조의 도구는 찾지 못했다. 칸반 TUI는 많지만, 여러 모양의 노트를 파일로 붙이는 범용 보드는 없다.

| 도구 | 하는 일 | 이 프로젝트와 다른 점 |
|---|---|---|
| [tuiboard](https://github.com/NazzarenoGiannelli/tuiboard) | 마크다운 칸반에 플래너·일정·에이전트 세션 보기를 더한 TUI | 구역이 고정되어 있고 새 패널을 붙일 수 없다. 읽기 전용 상태 파일은 하나만 지정한다. |
| [kanban-md](https://github.com/antopolskiy/kanban-md) | 태스크 하나가 파일 하나인 에이전트용 칸반 CLI·TUI | 칸반 전용이다. 에이전트는 주로 CLI 명령으로 조작한다. |
| [claude-canvas](https://github.com/dvdsgl/claude-canvas) | Claude Code가 tmux 분할 pane에 TUI를 띄우게 하는 도구 | Claude Code와 tmux 전용이고, 지원하지 않는 개념 증명이다. 상주하는 보드가 아니다. |
| [sidecar](https://github.com/marcus/sidecar) | 에이전트 옆에서 diff·파일·대화 기록·태스크를 보는 작업 공간 | 에이전트가 만든 내용을 붙이는 구조가 아니고 범위가 크다. |
| [tui-dashboard](https://github.com/lyuangg/tui-dashboard) | YAML로 셸 명령 출력을 위젯에 배치하는 대시보드 | 설정 파일이 필요하고, 화면에서 내용을 고칠 수 없다. |
| [Backlog.md](https://github.com/MrLesk/Backlog.md) | 마크다운 태스크 관리와 칸반 | 칸반·태스크 전용이다. |
| [redthread](https://github.com/B33pBeeps/redthread) | 메모지를 끌어다 놓고 실로 잇는 터미널 코르크보드 | 사람이 마우스로 쓰는 메모 도구다. 칸반·체크리스트·로그 같은 모양이 없다. 저장 형식과 에이전트 연동 여부는 확인하지 않았다. |

차별점은 한 문장이다. **폴더에 파일을 넣으면 노트가 붙고, 에이전트 종류와 터미널 종류를 가리지 않는다.**

## 3. 범위

### 처음 버전에 넣는 것

- 노트의 네 가지 모양: 일반 노트, `board`, `checklist`, `log`
- 폴더 감시와 자동 갱신
- 흐름 배치, 모달, 빠른 끄적이기, 모양 카탈로그
- TUI에서의 수정이 파일에 저장되는 공유 상태
- `init` 명령과 에이전트 안내문

### 넣지 않는 것

- 에이전트 실행·제어, 에이전트 세션 감시
- Linear, GitHub 같은 외부 서비스 동기화
- 실행 중에 끼우는 플러그인
- 노트 자유 배치(끌어다 놓기), 배치 설정 파일
- 여러 프로젝트를 한 화면에 모으기
- MCP 서버, 노트 조작용 CLI 명령
- TUI 안의 본문 편집기 (`$EDITOR`를 연다)

## 4. 핵심 개념

화면은 노트의 모음이고, **노트 하나는 `.stickypane/` 폴더 안의 마크다운 파일 하나**다.

- 파일을 만들면 노트가 붙는다.
- 파일을 고치면 노트가 갱신된다.
- 파일을 지우면 노트가 떨어진다.

저장소는 이 폴더가 전부다. 데이터베이스도, 설정 파일도, 실행 중인 서버도 없다. 에이전트와 사람과 TUI가 같은 파일을 읽고 쓴다.

### 폴더

```
프로젝트/
└── .stickypane/
    ├── 10-auth-board.md
    ├── 20-progress.md
    ├── auth-design.md
    ├── 배포-전에-env-확인.md
    ├── worklog.md
    └── archive/          떼어 낸 노트가 옮겨지는 곳
        └── old-notes.md
```

- TUI는 현재 디렉터리에서 위로 올라가며 `.stickypane/`를 찾는다. `stickypane <경로>`로 직접 지정할 수 있다.
- 폴더 바로 아래의 `*.md` 파일만 노트가 된다. `archive/`를 비롯한 하위 폴더와 다른 확장자는 무시한다.
- `.stickypane/`를 git에 올릴지는 사용자가 정한다. `init`은 `.gitignore`를 건드리지 않는다.

## 5. 파일 형식

### 가장 단순한 노트

머리말이 없는 마크다운 파일은 일반 노트다. 다음 한 줄짜리 파일이 온전한 노트다.

```markdown
배포 전에 env 확인하기
```

### 머리말

모든 항목이 선택이다.

```markdown
---
type: board
title: 인증 작업
color: blue
pin: true
---
```

| 키 | 값 | 기본값 |
|---|---|---|
| `type` | `note`, `board`, `checklist`, `log` | `note` (일반 노트) |
| `title` | 노트 제목 | 일반 노트는 제목 없음, 다른 모양은 파일 이름 |
| `color` | `yellow`, `pink`, `blue`, `green`, `purple`, `orange` | 파일 이름으로 정해지는 색 |
| `pin` | `true`면 화면 맨 위에 고정 | `false` |

- 일반 노트는 제목이 없어도 된다. 메모지처럼 내용만 보인다.
- `color`가 없으면 파일 이름을 해시해 여섯 색 중 하나를 고른다. 같은 노트는 항상 같은 색이다.
- 모르는 키는 그대로 보존한다. 모르는 `type` 값은 일반 노트로 취급해 원문을 보여 준다. 모르는 `color` 값은 기본 규칙을 따른다.

### 일반 노트 (`note`)

본문 전체를 마크다운으로 렌더링한다. 한 줄 메모부터 긴 보고서까지 모두 이 모양이다.

### board

`## ` 제목이 칸이고, 그 아래 최상위 목록 항목이 카드다. 항목 아래 들여쓴 줄은 그 카드의 상세 내용이다.

```markdown
---
type: board
title: 인증 작업
---
## 할 일
- 결제 연동
## 진행 중
- 로그인 API
  - 토큰 갱신은 다음 단계로 미룸
## 완료
- DB 스키마
```

- 카드를 옮기는 것은 항목을 (들여쓴 줄과 함께) 다른 제목 아래로 옮기는 것이다.
- 칸 이름과 개수는 자유다. 첫 `## ` 제목 앞의 본문은 보드 설명으로 모달에만 보여 준다.

### checklist

본문의 `- [ ]`, `- [x]` 줄이 항목이다. 진행률은 체크한 항목 수를 전체 항목 수로 나눈 값이다. 체크박스가 아닌 줄(제목, 설명)은 그대로 보여 준다.

```markdown
---
type: checklist
title: 로그인 API
---
- [x] 엔드포인트 추가
- [x] 입력 검증
- [ ] 테스트 작성
```

### log

본문의 각 줄이 로그 한 줄이다. 노트는 끝부분을 보여 주고, 줄이 추가되면 따라간다. 에이전트는 파일 끝에 줄을 덧붙이기만 하면 된다. 줄 형식은 자유다.

```markdown
---
type: log
title: 작업 로그
---
14:02 테스트 통과
14:10 리뷰 반영 시작
```

## 6. 화면과 조작

### 보드 화면

```
╭ 📌 인증 작업 ────────────────────────────────────╮
│ 할 일 (1)     진행 중 (1)     완료 (1)           │
│ 결제 연동     로그인 API      DB 스키마          │
╰──────────────────────────────────────────────────╯
╭ 로그인 API ───────────╮ ╭───────────────────────╮
│ ▓▓▓▓▓▓░░░ 2/3         │ │ 배포 전에 env 확인하기│
│ ☐ 테스트 작성         │ ╰───────────────────────╯
╰───────────────────────╯ ╭ ● 인증 설계 ──────────╮
╭ 작업 로그 ────────────╮ │ ## 결정 사항          │
│ 14:02 테스트 통과     │ │ 토큰은 세션 쿠키로 ...│
│ 14:10 리뷰 반영 시작  │ ╰───────────────────────╯
╰───────────────────────╯
 n 끄적이기  enter 열기  a 모양 골라 추가  ? 도움말
```

**모양새**: 노트는 모서리가 둥근 테두리로 그리고, 테두리와 제목을 노트 색으로 칠한다. 배경은 칠하지 않는다. 터미널 테마와 마크다운 렌더링이 깨지지 않게 하기 위해서다. `NO_COLOR`가 설정되어 있거나 터미널이 색을 지원하지 않으면 테두리만 그린다.

**정렬**: 고정한 노트가 먼저, 그다음은 파일 이름순이다. 수정 시각으로 정렬하지 않는다. 에이전트가 파일을 갱신할 때마다 노트가 자리를 옮기면 화면을 읽을 수 없기 때문이다. 순서를 바꾸고 싶으면 파일 이름 앞에 숫자를 붙인다.

**배치**: 노트의 최소 폭은 36칸이다. 열 수는 `pane 폭 ÷ 36`의 몫이고 최소 1이다. `board`는 한 줄 전체를 차지하고, 나머지는 한 열을 차지한다. 폭이 좁으면 모든 노트가 한 줄에 하나씩 쌓인다. 화면보다 길면 세로로 스크롤한다.

**미리보기 높이**: 모양마다 상한이 있고, 내용이 짧으면 그만큼만 차지한다. 일반 노트 6줄, `board` 칸당 카드 5장, `checklist` 진행률 막대와 남은 항목 4개, `log` 마지막 5줄.

**갱신 표시**: 마지막으로 포커스한 뒤에 파일이 바뀐 노트는 제목 자리에 `●`를 붙인다. 포커스하면 사라진다.

**빈 화면**: 노트가 하나도 없으면 "아직 붙은 노트가 없어요. n을 눌러 끄적여 보세요."를 보여 준다.

### 띄우는 방법

일반 터미널 프로그램이라 어디서든 실행하면 된다. 터미널 종류별 연동 코드는 두지 않고, README에 다음 사용법을 안내한다.

| 방식 | 명령 |
|---|---|
| tmux에서 옆 pane에 상주 | `tmux split-window -h stickypane` |
| tmux에서 팝업으로 잠깐 열기 | `tmux display-popup -E stickypane` |
| wezterm에서 옆 pane에 상주 | `wezterm cli split-pane --right -- stickypane` |

pane 크기가 바뀌면 그 폭에 맞춰 배치를 다시 계산한다.

### 키

보드 화면에서는 노트를 고르고 관리한다.

| 키 | 동작 |
|---|---|
| 방향키, `h` `j` `k` `l`, `tab` | 포커스 이동 |
| `enter` | 모달로 열기 |
| `n` | 빠른 끄적이기 |
| `a` | 모양을 골라 노트 추가 |
| `c` | 색 바꾸기 (누를 때마다 다음 색) |
| `p` | 고정 켜기/끄기 |
| `x` | 떼어 내기 (`archive/`로 옮김) |
| `D` | 삭제 (확인을 받음) |
| `R` | 제목 바꾸기 |
| `e` | `$EDITOR`로 파일 열기 |
| `r` | 폴더 다시 읽기 |
| `q` | 종료 |

모달에서는 노트 하나의 내용을 다룬다. `esc`로 닫는다.

| 모양 | 모달의 키 |
|---|---|
| 일반 노트 | 스크롤 |
| board | `h` `l`로 칸 이동, `j` `k`로 카드 이동, `H` `L`로 카드를 옆 칸으로, `J` `K`로 칸 안에서 순서 변경, `n`으로 카드 추가, `enter`로 카드 상세 보기 |
| checklist | `j` `k`로 이동, `space`로 체크 켜기/끄기, `n`으로 항목 추가 |
| log | 스크롤, `G`로 끝으로 가서 따라가기 |

### 빠른 끄적이기

`n`을 누르면 한 줄 입력창이 뜬다. 입력하고 `enter`를 누르면 그 줄을 본문으로 하는 일반 노트가 바로 붙는다. 모양도 제목도 묻지 않는다.

### 모양 카탈로그

`a`를 누르면 모양 목록이 뜬다. 모양을 고르고 제목을 입력하면 템플릿으로 파일을 만든다.

### 파일 이름

TUI가 만드는 파일의 이름은 입력한 글(끄적이기는 본문, 카탈로그는 제목)에서 만든다. 글자와 숫자는 한글을 포함해 그대로 두고, 공백은 하이픈으로 바꾸고, 나머지 문자는 지우고, 40자에서 자른다. 결과가 비면 `note-<날짜시각>`을 쓴다. 같은 이름이 있으면 뒤에 숫자를 붙인다.

## 7. 공유 상태

TUI에서의 수정은 모두 같은 파일에 저장된다. 에이전트는 다음에 파일을 읽을 때 사용자가 바꾼 내용을 본다.

| TUI 동작 | 파일에 일어나는 일 |
|---|---|
| 끄적이기, 모양 골라 추가 | 새 파일 생성 |
| 카드를 옆 칸으로 옮김 | 목록 항목이 다른 `## ` 제목 아래로 이동 |
| 카드 추가 | 포커스한 칸의 마지막 카드 뒤에 목록 항목 한 줄 추가 |
| 체크리스트 항목 추가 | 마지막 체크박스 줄 뒤에 `- [ ]` 한 줄 추가 (체크박스가 없으면 본문 끝) |
| 체크 켜기/끄기 | `- [ ]`와 `- [x]` 사이 전환 |
| 색 바꾸기 | 머리말의 `color` 변경 (머리말이 없으면 만듦) |
| 고정 | 머리말의 `pin` 변경 (머리말이 없으면 만듦) |
| 제목 바꾸기 | 머리말의 `title` 변경 (머리말이 없으면 만듦) |
| 떼어 내기 | 파일을 `archive/`로 이동 |
| 삭제 | 파일 삭제 |

### 쓰기 규칙

TUI는 화면에 들고 있던 내용을 통째로 덮어쓰지 않는다. 수정은 "이 카드를 저 칸으로" 같은 **의도**로 표현하고, 쓰는 순간에 다음을 한다.

1. 파일을 새로 읽는다.
2. 방금 읽은 내용에 의도를 적용한다.
3. 같은 폴더의 임시 파일에 쓰고 이름을 바꿔 교체한다.

2에서 대상을 찾지 못하면(그사이 에이전트가 그 카드를 지웠거나 고쳤으면) 쓰지 않고, 화면을 새로 고친 뒤 "그사이 파일이 바뀌어 적용하지 못했습니다"를 한 줄로 알린다. 이렇게 하면 에이전트의 변경을 TUI가 지우는 일이 없다.

머리말을 고칠 때는 바꾸는 키의 줄만 고친다. 다른 키, 키 순서, 본문은 바이트 그대로 둔다.

## 8. 에이전트 연동

연동 장치는 안내문 하나뿐이다. `stickypane init`이 다음을 한다.

1. `.stickypane/`를 만들고, 조작법을 적은 환영 노트 `welcome.md`를 하나 붙여 둔다.
2. 프로젝트 루트의 `AGENTS.md`와 `CLAUDE.md` 중 있는 파일에 안내문을 덧붙인다. 둘 다 없으면 `AGENTS.md`를 만든다. `--no-agent-docs`를 주면 이 단계를 건너뛴다.
3. 안내문은 `<!-- stickypane:start -->`와 `<!-- stickypane:end -->` 사이에 넣는다. 다시 실행하면 그 구간만 교체한다.

안내문은 30줄 안쪽이고 다음을 담는다.

- 폴더 위치와 "파일 하나가 노트 하나"라는 규칙
- 네 가지 모양의 형식
- 쓰는 태도: 기억해 둘 것, 결정한 것, 진행 상황을 짧게 끄적인다. 한 줄짜리 파일이면 충분하고 머리말은 필요할 때만 쓴다. 진행 상황이 바뀌면 해당 노트를 고친다.
- 읽는 태도: 사용자가 보드에서 노트를 고쳤을 수 있으니, 노트를 고치기 전에 다시 읽는다.

`stickypane guide`는 같은 안내문을 표준 출력으로 내보낸다.

훅, MCP 등록, 에이전트별 설정은 없다.

## 9. 구조

Go로 작성하고 TUI는 Bubble Tea 계열 라이브러리(Bubble Tea, Lip Gloss, Glamour)로, 파일 감시는 fsnotify로 한다.

용어를 구분한다. **노트**는 파일이고 사용자에게 보이는 말이다. **위젯**은 코드 안에서 한 모양의 노트를 그리고 조작하는 단위다.

```
cmd/stickypane/          진입점. 인자 해석 후 app 또는 initcmd 호출
internal/doc/           머리말과 본문 분리, 머리말 줄 단위 수정
internal/store/         폴더 찾기, 읽기, 감시, 의도 적용, 떼어 내기·삭제·생성
internal/widget/        Kind 등록부와 Widget 인터페이스
internal/widget/note/
internal/widget/board/
internal/widget/checklist/
internal/widget/logview/
internal/layout/        폭과 노트 목록으로 위치 계산 (순수 함수)
internal/app/           Bubble Tea 모델: 보드 화면, 모달, 끄적이기, 카탈로그
internal/initcmd/       init, guide, 안내문, 환영 노트
```

의존 방향은 한쪽이다. `app`이 `store`, `widget`, `layout`을 쓴다. 위젯 패키지는 `doc`과 `widget`만 알고, `store`와 `app`과 다른 위젯을 모른다.

### 위젯 인터페이스

```go
// Kind는 노트의 모양 하나를 등록부에 올리는 단위다.
type Kind struct {
    Name     string                              // 머리말의 type 값
    FullRow  bool                                // 한 줄 전체를 차지하는가
    Template func(title string) []byte           // 카탈로그가 만드는 새 파일 내용
    Parse    func(d doc.Document) (Widget, error)
}

type Widget interface {
    Preview(width, height int) string            // 보드 화면의 미리보기
    View(width, height int) string               // 모달의 전체 화면
    Update(msg tea.KeyMsg) (Widget, Op)          // 모달의 키 입력. 파일을 바꿔야 하면 Op를 돌려준다
}

// Op는 파일에 적용할 의도다. 대상을 찾지 못하면 ErrConflict를 돌려준다.
type Op interface {
    Apply(d doc.Document) (doc.Document, error)
}
```

위젯은 파일을 직접 쓰지 않는다. `Op`를 돌려주면 `store`가 7절의 쓰기 규칙대로 적용한다. 그래서 위젯은 파일 시스템 없이 테스트할 수 있다.

테두리, 제목, 색, 고정 표시는 `app`이 모든 노트에 똑같이 그린다. 위젯은 테두리 안쪽만 그린다.

새 모양을 추가하려면 `internal/widget/<이름>/` 패키지를 만들고 등록부에 `Kind` 하나를 추가한다.

### 파일 감시

`.stickypane/` 폴더 하나를 감시한다. 이벤트가 오면 100ms 동안 모았다가 폴더 전체를 다시 읽는다. 에디터와 에이전트는 저장할 때 임시 파일을 만들고 이름을 바꾸는 경우가 많아서, 이벤트를 파일별로 해석하지 않고 폴더를 다시 읽는 쪽이 단순하고 정확하다. 노트 수가 수십 개 수준이라 비용 문제는 없다.

감시를 시작하지 못하면 화면 아래에 알리고 `r` 키로 수동 갱신하게 한다.

## 10. 오류 처리

| 상황 | 동작 |
|---|---|
| 머리말 YAML이 깨짐 | 오류 노트로 표시한다. 오류 내용과 원문을 함께 보여 준다. 파일은 건드리지 않는다. |
| 모양의 형식에 맞지 않음 (예: 칸이 없는 board) | 빈 상태로 그리고 형식 안내 한 줄을 보여 준다. |
| 모르는 `type` | 일반 노트로 취급한다. |
| 파일이 1MB를 넘음 | log는 마지막 64KB만 읽는다. 다른 모양은 오류 노트로 표시한다. |
| 쓰기 직전에 대상이 바뀜 | 쓰지 않고 화면을 새로 고친 뒤 알린다. |
| 파일 쓰기 실패 | 화면 아래에 오류를 알리고 화면 상태를 파일 기준으로 되돌린다. |
| `.stickypane/`가 없음 | `stickypane init`을 안내하고 종료한다. |

원칙은 하나다. **형식이 틀려도 내용을 숨기거나 잃지 않는다.**

## 11. 테스트

- **doc**: 머리말 분리와 줄 단위 수정. 모르는 키, 키 순서, 본문이 바이트 그대로 유지되는지 확인한다. 머리말이 없는 파일에 머리말을 만드는 경우를 포함한다.
- **위젯**: 모양별로 "파일 내용 → 미리보기·모달 출력"을 기준 결과 파일과 비교한다. `Op`는 "적용 전 내용 → 적용 후 내용"과 충돌 사례를 표로 테스트한다.
- **layout**: 폭과 노트 목록에 대한 위치 계산을 표로 테스트한다. 폭 40, 80, 120을 포함한다.
- **store**: 임시 폴더에서 읽기, 감시, 의도 적용, 쓰는 사이 외부 수정이 끼어드는 경우, 파일 이름 만들기(한글, 빈 결과, 중복)를 테스트한다.
- **app**: 키 입력을 흘려 넣고 화면을 확인하는 테스트를 몇 개 둔다. 열기, 카드 옮기기, 끄적이기, 카탈로그로 노트 만들기를 다룬다.
- **initcmd**: 안내문 삽입이 여러 번 실행해도 같은 결과인지 확인한다.

에이전트가 안내문만으로 노트를 다루는지는 자동화하지 않고, 릴리스 전에 Claude Code와 Codex로 직접 확인한다.

## 12. 배포

- 단일 실행 파일. macOS와 Linux를 지원한다. Windows는 처음 버전의 대상이 아니다.
- GitHub Releases, Homebrew tap, `go install` 세 경로로 제공하고 GoReleaser로 자동화한다.
- 라이선스는 MIT다.
- README와 에이전트 안내문은 영어로 쓴다. README의 첫 문장과 화면 예시는 1절의 정체성(가볍게 끄적이는 노트 보드)을 그대로 전한다.

## 14. 이름

이름은 `stickypane`이다. tmux의 pane이라는 말을 그대로 쓰고, sticky가 "붙이는 메모지"와 "옆에 붙어 있는 창" 두 뜻을 함께 담는다. 2026-10-01 기준으로 같은 이름의 명령어, Homebrew 패키지, 프로젝트를 찾지 못했다.

폴더 이름(`.stickypane/`), 명령어(`stickypane`), 안내문 표식(`<!-- stickypane:start -->`)이 모두 이 이름을 따른다.

제외한 후보는 다음과 같다.

| 후보 | 제외한 이유 |
|---|---|
| `corkboard` | redthread가 "ASCII corkboard"를 내세우고 있어 헷갈린다. |
| `tack` | 같은 이름의 AI 코딩 CLI가 있다. |
| `scribble`, `scrawl` | 같은 이름의 터미널 노트 도구가 있다. |
| `jot` | macOS 기본 명령어 `/usr/bin/jot`과 겹친다. |
| `doodle` | 일정 조율 서비스 Doodle과 이름이 같다. |
| `agentpad`, `agentpane`, `agentboard`, `paneboard` | 같은 이름의 프로젝트가 있고 대부분 AI 에이전트 도구다. |
| `sidenotes` | Homebrew에 같은 이름의 패키지가 있다. |
